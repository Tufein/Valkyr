# 7.4 — emulator setup, not only the check: task list

*Tools → Emulator check* already knows what is missing. These tickets add the step after it: what
to do about it, with a preview of everything the app writes. Paths are relative to
`app/src/main/java/com/tufein/valkyr/`.

The parts to build on, as they exist now:

- The check: `util/EmulatorCheck.kt` — `Status { STANDALONE, RETROARCH, MISSING, UNSUPPORTED }`
  (L10), `coverage()` (L34) with `suggestions` (L22), `coverages()` (L54). Its screen
  (`ui/screens/tools/EmulatorCheckScreen.kt`) only lists installed packages through
  `EmulatorCatalog.allPackages()` and `ApkAssets.isInstalled`, and says plainly that it installs
  nothing.
- The knowledge: `util/EmulatorCatalog.kt` — `PlaySystem` (L26–69) carries the console words, the
  preferred libretro cores and the disc flag; `Emulator` (L136–147) carries packages, formats,
  archives and a `Confidence` (L14); `systemOf()` (L450), `targetsFor()` (L524),
  `installedVariant()` (L498), `coreLabels` (L503). Every package that must stay visible on
  Android 11+ is listed in `AndroidManifest.xml` under `<queries>` (L20–92; `queriesXml()` at L537
  says so).
- Launching: `data/service/GameLaunchService.kt` — `choices()` (L103), `catalogueTargets()` (L181),
  `setPreferred()` (L140), `launch()` (L212) with `LaunchOutcome` (L65); recipes and keys in
  `util/PlayRecipe.kt` (`GameLaunchKeys` L12, `corePath()` L146, `configPath()` L149, disc entry
  priority L127), per-game overrides in `util/GameEmulatorOverrides.kt` and
  `data/service/GameEmulatorPreferences.kt`.
- Readiness per game: `util/GameReadiness.kt` (`emulatorState()` L14) and
  `data/service/GameReadinessService.kt` (`GameReadyReport` L16, `check()` L29: readable files,
  sheet references through `util/SetChecker.kt`, BIOS through `util/BiosCatalog.kt` +
  `data/service/BiosService.kt` (L33) against `bios_dir`, emulator).
- BIOS from the server: `data/service/RommFirmwareService.kt` and `util/RommFirmwareMatcher.kt`,
  with the card on the game page in `ui/screens/cloud/sections/RommFirmwareCard.kt`.
- Disc lists: `util/PlaylistPlanner.kt` (`plan()` L33) already writes `.m3u` after a download when
  `autoM3u` is on (`data/service/PostDownloadService.kt` L65–76) and `util/LibraryRepair.kt`
  rewrites dead ones. `.lpl` playlists and the default core per system live in
  `util/RetroArchPlaylists.kt` (`defaultCore()` L81) and its screen.
- A guided flow already exists for a different question: `util/NewHandheldPlan.kt` (`Action` L35)
  and `ui/screens/tools/NewHandheldScreen.kt` open the right screen per step and never act
  themselves. `util/HandoffGuide.kt` is the model for explaining why something cannot be done.

## 1. A setup plan per console, in pure logic first

**Why.** The check knows the gap; nothing turns the gap into steps.

**What.** `util/EmulatorSetupPlan.kt`: from `PlaySystem`, `Emulator`, the installed packages, the
BIOS report and the current preferences, a list of steps — core to pick (or app to install, with
its name and where to get it), BIOS files wanted with their folder, save and state folder, disc
list if the game has several — each with the exact file or setting it would write and the
verification that follows. No Android calls, no UI: the same style as `NewHandheldPlan` and
`PlaylistPlanner`.

**Files.** new `util/EmulatorSetupPlan.kt`, `util/EmulatorCatalog.kt`, `util/EmulatorCheck.kt`,
`util/BiosCatalog.kt`, `util/PlayRecipe.kt`, `util/GameEmulatorOverrides.kt`, new
`app/src/test/java/com/tufein/valkyr/util/EmulatorSetupPlanTest.kt`.

**Done when.** The test covers: a standalone app present, RetroArch with a core candidate, nothing
installed, an unsupported system, and a two-disc game; every step names what it writes.

## 2. The setup screen, with a preview before anything is written

**Why.** Users get "missing" today and have to know which screen fixes it.

**What.** `EmulatorSetupScreen` reached from the check's *missing* row: steps in order, each one
either opening an existing screen (BIOS folder, RetroArch cores, save folders) or applying a
setting with a preview line "this writes: …". The `.m3u` and `.lpl` steps reuse the existing
preview-then-write discipline: the old file goes to Trash and recovery first, nothing is replaced
that already exists. Installing is never silent — the step says which app, opens the store page or
the project site, and re-checks afterwards.

**Files.** new `ui/screens/tools/EmulatorSetupScreen.kt` + `EmulatorSetupViewModel.kt`,
`ui/screens/tools/EmulatorCheckScreen.kt` (the entry), `ui/screens/tools/RetroArchPlaylistsScreen.kt`
and `ui/screens/tools/BiosScreen.kt` (the same actions, from one place),
`data/service/GameReadinessService.kt` (verify step), `ui/navigation/NavRoutes.kt`,
`MainActivity.kt`, `ui/screens/tools/ToolsHubScreen.kt`, `util/SearchIndex.kt` (findable as a
screen), new `app/src/main/res/values/strings_v74_setup.xml` plus the six locale copies.

**Done when.** Every action is listed before it runs, cancelling leaves nothing half-written, and
a second visit shows the steps already satisfied.

## 3. A test launch that says what happened

**Why.** `LaunchOutcome.FAILED` today means "no activity answered", not "what the emulator said".

**What.** Keep the launch itself; add a short report around it: which package and version answered,
which recipe and confidence were used, whether the file needed unpacking
(`GameReadiness.emulatorState`), and — when the game disappears again within a few seconds — the
honest sentence "it started and stopped again, here is what to look at" with the BIOS and core
steps reopened. Nothing is read from another app's private files.

**Files.** `data/service/GameLaunchService.kt`, `util/GameReadiness.kt`,
`util/PlayRecipe.kt`, the new setup screen, `util/HandoffGuide.kt` (the unknown-emulator case).

**Done when.** A launch with a missing BIOS file names the file instead of "failed", and the
unknown-emulator path still gives the manual instructions rather than a dead end.

## 4. The checklist tells you when it is really done

**Why.** *Set up a new handheld* opens screens; it cannot say the console now works.

**What.** Feed `NewHandheldPlan`'s steps from the setup plan's state, so the "emulators" line turns
green when the readiness check passes and names what still blocks.

**Files.** `util/NewHandheldPlan.kt`, `ui/screens/tools/NewHandheldScreen.kt`,
`util/EmulatorSetupPlan.kt`, `util/HealthRules.kt`.

**Done when.** `NewHandheldPlanTest` covers a console that went from missing to ready, and the
checklist no longer points at a screen that has nothing left to do.

## Order of work

1 is pure and testable today; 2 is the screen; 3 makes the promise believable; 4 closes the loop
with the checklist. None of them installs anything, and none touches a game file without a preview.

## Where this runs

1 and 4 are unit tests. 2 and 3 need a device with a couple of emulators installed — the checks
that matter are "the store page opens", "the core choice sticks" and "a test launch reports the
truth", and those cannot be faked. `EmulatorCheckTest`, `EmulatorCatalogTest`,
`GameReadinessEmulatorTest`, `BiosCatalogTest` and `PlaylistPlannerTest` are the existing homes
for the regression cases.
