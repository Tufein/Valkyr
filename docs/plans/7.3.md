# 7.3 — save sync for more emulators: task list

Saves that travel without typing a path, and one conflict decision instead of twenty. Paths are
relative to `app/src/main/java/com/tufein/valkyr/`.

What the code does today:

- One pure planner decides everything: `util/SaveSyncPlanner.kt` — `plan()` (L153–264) matches
  first on the remembered record, then on filename plus the emulator's folder token, and returns
  NEWER / DEVICE_NEWER / SERVER_NEWER / BOTH_CHANGED / IDENTICAL / UNMAPPED / TOO_LARGE. The
  conflict identity is `key(kind, path)` (L363, lowercased path); `kindOf()` (L122) calls
  something a state by name (`.state`, `.state1`, `.state.auto`).
- `util/SaveSyncEngine.kt` executes it: `sync()` (L103) with a deletions brake
  (`MIN_DELETIONS_WITHOUT_ASKING = 3`, L325), and `resolve()` / `resolveKeepBoth()` (L205, L217)
  which handle **one conflict at a time**. `util/SaveMerge.kt` holds the verdict and the options
  (`preferNewerServer`, `nonDestructive`).
- RomM is the only server: `RommSaveServer` inside `data/service/SaveSyncService.kt` (L311) over
  `data/service/RommClient.kt` (`saves()` L276, `downloadSave()` L303, `uploadSave()` L321). The
  `SaveServer` / `SaveStore` pairs (engine L37, L48) already allow another one.
- Shapes live in two files. `util/EmulatorSaveLayouts.kt` has `SaveFolderLayout` — FILES,
  MEMCARDS, SAVEDATA, PS2_MEMCARDS, GC_MEMCARDS — with `MAX_CARD_BYTES = 72 MB` (L85),
  `sizeLimit()` (L142), `holdsSeveralSaves()` (L148), `isChosenGameOnly()` (L154) and
  `innerPath()` (L310), which finds `memcards` / `GC` / `PSP/SAVEDATA` inside a chosen tree by
  folder signature. `util/EmulatorSaveFolders.kt` has the `Preset` table (L66–76) and `presets`
  (L78–95), stored as JSON under `save_sync_emulator_folders` (`data/local/AppSettings.kt` L83).
- Presets exist for DuckStation, PPSSPP, AetherSX2/NetherSX2 and both Dolphins as card shapes, and
  as plain FILES for DraStic, melonDS, mGBA, Pizza Boy, the .emu ports and Snes9x EX+. For that
  last group `folderHint` is **prose only** ("melonDS saves folder"): nothing locates the folder.
- Folders come from two pickers (`save_sync_saves_dir`, `save_sync_states_dir`,
  `data/local/SettingsDataStore.kt` L62/L64) plus `EmulatorPresetDialog`
  (`ui/screens/settings/savesync/SaveSyncScreen.kt` L700): the user points at a tree and picks a
  preset by hand.
- Conflicts are one row per file with two buttons (`conflictRows` L406, `ConflictRow` L558) and a
  "keep both" pill. No selection state, no batch call.
- Limits differ per shape and every new layout must say which one it uses: 64 MB per file
  (`SaveSyncService` L88), 72 MB for cards, 64 MB / 4096 entries for Dolphin bundles
  (`util/DolphinSaveBundles.kt` L67–70), 16 MB for a hand-off (`util/SaveHandoff.kt` L32).
- Safety copies: `util/VerifiedSafetyCopies.kt` writes to `files/save-backups/`, `util/SaveBackups.kt`
  keeps 5 per game, 30 days, trash 14 days, trimmed after every sync.
- Folder mode (Syncthing) reuses the planner and the store (`util/SyncthingFolderSync.kt`,
  `data/service/SyncthingFolderService.kt`) but accepts **only** `layout == FILES` (the branch at
  `SaveSyncService` L791) and has no background scheduler, unlike RomM sync
  (`data/service/SaveSyncScheduler.kt`).

## 1. Fill the preset table with the emulators that are really there

**Why.** `util/EmulatorCatalog.kt` already knows melonDS (L284), WatermelonDS (L289), DraStic
(L298), M64Plus FZ (L306), the Switch family (L345–376), Flycast (L378) and Redream (L382); the
preset table knows none of their save shapes.

**What.** Presets for the DS, N64, Dreamcast and Switch emulators and for RetroArch's per-core
folders, each with the folder names it actually writes, its layout, its size limit and whether one
file holds several games.

**Files.** `util/EmulatorSaveFolders.kt` (presets, `folderHint`), `util/EmulatorSaveLayouts.kt`
(every `when (layout)` branch: `memoryCard`, `searchTerms`, `matchRom`, `belongsToGame`,
`sizeLimit`, `holdsSeveralSaves`, `isChosenGameOnly`, `innerPath`, `toJson`/`fromJson`),
`util/SaveSyncPlanner.kt` (`kindOf`), `data/service/SaveSyncService.kt` (`SafSaveStore.list` L337,
`read`/`write` L479–532, layout branches at L480/L527/L1155/L1166),
`app/src/main/AndroidManifest.xml` (`<queries>` L20–92) for any new package, new
`app/src/main/res/values/strings_v73_saves.xml` plus the six locale copies.

**Done when.** `EmulatorSaveFoldersTest` and `EmulatorSaveLayoutsTest` cover every new row, a
card-shaped DS save and a Switch save database pass a sync in the style of
`MemcardSavedataSyncTest`, and `fromJson` still drops an unknown layout so an older app survives.

## 2. Propose the folders instead of asking for them

**Why.** `innerPath()` already recognises a shape inside a tree; today the user still types or
picks.

**What.** One chosen root plus the installed packages (`util/ApkAssets.kt`,
`EmulatorCatalog.allPackages()`) run through `innerPath()` and the signature sets, offering the
recognised folders as a proposal the user edits before it is saved. Where a folder cannot be read
— Android keeps `Android/data` behind other apps' permissions, see the note in
`util/PlayRecipe.kt` L156 — say so and keep the text hint and the manual dialog.

**Files.** `ui/screens/settings/savesync/SaveSyncScreen.kt`, `SaveSyncViewModel.kt`
(`addEmulatorFolder` L69), `util/EmulatorSaveLayouts.kt`, `util/EmulatorSaveFolders.kt`,
`util/StorageHelper.kt`, `util/SettingSchema.kt`.

**Done when.** With melonDS, DraStic and M64Plus FZ installed and one root chosen, the screen
proposes three correct folders; propose/accept/reject is covered at view-model level, and the
manual path still works.

## 3. One conflict decision for a batch

**Why.** `SaveSyncService.resolveWith()` (L205) takes the lock per conflict and each resolve
re-lists the device folder and the server, so 300 conflicts cost 300 full listings.

**What.** `resolveAll(pick, conflicts)` on the engine: one listing round, one lock, then the same
per-file safety (safety copy first, `.part` write, verify, drop by `key(kind, path)`). In the UI a
summary sheet first — how many differ, newest side per group, one choice for all — with the
per-file list behind *show me*.

**Files.** `util/SaveSyncEngine.kt`, `data/service/SaveSyncService.kt`,
`ui/screens/settings/savesync/SaveSyncScreen.kt`, `SaveSyncViewModel.kt`,
`util/SaveConflictInfo.kt`, `FolderModeRows.kt` (Syncthing conflicts already remember decided ids
through `FolderConflict.id`, `util/SyncthingFolderSync.kt` L91).

**Done when.** `SaveSyncEngineTest` shows a ten-conflict batch makes one listing pass and keeps
"keep both" naming safe, and the screen clears ten in one action.

## 4. Newest save on the game page, whatever the emulator

**Why.** The pictures come from `data/service/CloudSavesService.stateShots()` (L290) and
`ui/screens/cloud/saves/StateShotPair.kt`, which only know RetroArch's naming.

**What.** Per-layout thumbnail rules (state file, sidecar screenshot, memory-card slot) and a
newest-save line with its date, so a game shows its last save even when no emulator picture
exists.

**Files.** `data/service/CloudSavesService.kt`, `ui/screens/cloud/saves/StateShotPair.kt`,
`util/StatePreviews.kt`, `util/EmulatorSaveLayouts.kt`, `ui/screens/game/GamePage.kt`.

**Done when.** `StatePreviewsTest` covers two layouts, and a DuckStation card game shows a save
line with no thumbnail.

## 5. Folder mode: cards, bundles, and running by itself

**Why.** Syncthing mode syncs FILES only and never runs on a schedule, while RomM mode does both.

**What.** Let the card and pack shapes through `FolderSaveSync.sync()` (the deterministic
`SavePack` zip already exists in `EmulatorSaveLayouts.kt` L342), and give folder mode a scheduler
modelled on `SaveSyncScheduler.kt` with the same `util/BackgroundSyncPolicy.kt` notification rules.

**Files.** `util/SyncthingFolderSync.kt`, `data/service/SyncthingFolderService.kt`,
`data/service/SaveSyncScheduler.kt`, `util/BackgroundSyncPolicy.kt`, `FolderModeRows.kt`.

**Done when.** `SyncthingFolderSyncTest` covers a PPSSPP pack through folder mode, and a folder
mode sync runs without the screen being opened.

## Order of work

1 makes new emulators possible, 2 removes the typing, 3 removes the nagging, 4 and 5 are quality.
They all edit the same two tables, so they go in that order.

## Where this runs

1, 3, 4 and 5 are unit-testable with the existing fakes (`SaveSyncFakes.kt`: `TestClock`,
`FakeSaveStore`, `FakeSaveServer`). Ticket 2 needs a device with real emulators installed, and the
batch resolve deserves one run against a real RomM server — `RommSaveSyncLiveTest` is that
pattern.
