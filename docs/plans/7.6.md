# 7.6 — scale: task list

One library of about 100,000 games, scanned, searched and scrolled without waiting. Tickets
in order; each one ships on its own and leaves the app working as it does today. Paths are
relative to `app/src/main/java/com/tufein/valkyr/`.

Today's facts, so the tickets are aimed at the right places:

- Source scans already reuse unchanged listings: `util/ListingCheck.kt` (`PARSER_VERSION = 2`,
  `canReuse`, `conditionalHeaders`, `sameBody`, `canSkipMagnet`) with validators kept in
  `data/state/SourceScanResults.kt`. The verdict is **per source**, never per folder, and RomM
  has no validator at all.
- When a source did change, `DownloadableFileDao.replaceSource` deletes every row of that source
  and re-inserts all of it, so a one-file change costs a full rewrite plus a full FTS rewrite.
- Disk scanning walks everything, every time: `LibraryScanService.scan()`, `ownedKeys` in
  `LibraryIndexService`, and `LibraryToolsService.disk()` behind Storage and Duplicates.
  One `ContentResolver.query` per folder (`util/DiskScanner.kt`); no MediaStore is used.
- Search runs per keystroke: `HomeViewModel.setSearch` has no debounce (only recent searches do,
  1500 ms), and `LibraryQueryBuilder` keeps two measured traps in comments (FTS is slower than
  LIKE for words under 3 characters; a bad join order costs 16 s instead of 20 ms at 100k rows).
- Thresholds exist in `util/PerfCheck.verdictOf`: search 150 ms fast / 500 ms slow, first page
  100/300 ms, count 20/100 ms, shelves 300/1000 ms, cover decode 15/40 ms. No 100k library has
  ever been measured (`docs/PROFILING.md` says so plainly).
- Scans do not pause on battery or heat; downloads do (`util/PowerRules.kt`, `PowerMonitor`,
  `DownloadGate`), and `util/SmartStorage.kt` already has a byte budget per background run.

## 1. Folder fingerprints, recorded before they are used

**Why.** "Nothing changed here" needs a definition that survives a restart and notices deletions.

**What.** A pure `DirFingerprint` (entry count, total bytes, max mtime, and a hash of the sorted
`name|size|mtime` list) plus a `scan_state` table (`dirKey`, fingerprint, scannedAt) through a
`Migration16To17` written like `data/local/Migration15To16.kt` (pure `plan()`, unit-tested).
A pass that only writes fingerprints, changes no behaviour.

**Files.** `util/DiskScanner.kt`, new `util/DirFingerprint.kt`, `data/local/DogmatixDatabase.kt`,
new `data/local/Migration16To17.kt`, `data/service/LibraryScanService.kt` (walk records),
`data/service/LibraryIndexService.kt`.

**Done when.** `DirFingerprintTest` covers added / removed / size-changed / mtime-only-changed,
and a second walk of an unchanged folder tree writes identical rows.

## 2. Incremental disk scan behind a flag

**Why.** Ticket 1 makes "unchanged" measurable; this makes it useful.

**What.** `scan(incremental = true)` skips folders whose fingerprint matches, walks everything
whose children differ, and updates `ownedKeys` from the previous set plus the delta. Removals
and lost folder access are never treated as "unchanged": a folder that cannot be listed is
reported, not counted as empty.

**Files.** `LibraryScanService.kt`, `LibraryIndexService.kt`, `data/state/RescanStateHolder.kt`.

**Done when.** `ScanDiffTest` (pure) passes, and re-running a scan over an unchanged library does
no writes.

## 3. Row-level diffs for sources, and a validator for RomM and Homebrew Hub

**Why.** One changed listing line should not rewrite 40,000 rows and the FTS index with it.

**What.** `replaceSource` becomes a diff (`upsertSource`: insert new, update changed, delete
gone) so FTS only touches what moved; `ListingCheck` gains per-entry verdicts; RomM gets the
same `sameBody` treatment over its platform listing, Homebrew Hub hashes all its pages instead
of the first one.

**Files.** `data/local/dao/DownloadableFileDao.kt`, `data/service/DatabaseScrapingService.kt`,
`data/service/RommScrapingService.kt`, `util/ListingCheck.kt`.

**Done when.** `ListingCheckTest` and a new `RommScrapingServiceTest` (fake client) show
`unchanged = true` for a rescan with no moves, and `firstSeenAt` still marks genuinely new files.

## 4. A scan budget, and scans that pause like downloads do

**Why.** A background scan of 300 sources today ignores a flat battery and cannot be cancelled.

**What.** A pure `ScanBudgetPolicy` (sources per run, bytes parsed, stop on `PowerHold`, resume
next window), `AutoScanScheduler` feeding it the same settings downloads use, and a
`SourceScanService.cancel()` next to its mutex so the user can stop a scan and keep what is done.

**Files.** `util/AutoScanPolicy.kt`, new `util/ScanBudgetPolicy.kt`,
`data/service/AutoScanScheduler.kt`, `data/service/SourceScanService.kt`,
`data/service/PowerMonitor.kt`, `data/local/PowerRuleSettings.kt`.

**Done when.** `ScanBudgetPolicyTest` passes and a scan started at 18 % battery pauses with a
visible reason, the same sentence downloads use.

## 5. Snapshot cache for Storage, Overview and Duplicates

**Why.** Those three screens walk the whole disk on every visit.

**What.** One `DiskSnapshot` with a TTL, invalidated by `LibraryIndexService.requestRefresh()`,
a finished download, or a folder whose fingerprint moved. The first visitor still pays for a
real walk; the second does not.

**Files.** `data/service/LibraryToolsService.kt`, `LibraryScanService.overview()`,
`ui/screens/tools/StorageScreen.kt`, `ui/screens/tools/LibraryOverviewViewModel.kt`,
`util/DuplicateFinder.kt` (reads the snapshot).

**Done when.** `StorageSnapshotCacheTest` covers hit, miss and invalidation, and Statistics uses
`COUNT` queries instead of loading favourites and collections into memory.

## 6. Search that waits for you to stop typing

**Why.** Every keystroke re-runs a query over the whole library.

**What.** A 250–300 ms debounce on `_searchQuery` (the value `SearchAllScreen` already uses), a
per-query time-out with the LIKE fallback in `DownloadableFileRepository.withText`, and the
in-memory filtering caps (`SCAN_BATCH = 1500`, `SCAN_CAP = 60000`) turned into a stated budget
rather than a loop limit.

**Files.** `ui/screens/home/HomeViewModel.kt`, `data/repository/DownloadableFileRepository.kt`,
`data/local/queries/LibraryQueryBuilder.kt`.

**Done when.** `HomeSearchBudgetTest` shows ten keystrokes become one query, and
`LibraryQueryBuilderTest` still covers the FTS/LIKE shapes.

## 7. Real cover scrolling, measured and then improved

**Why.** `PerfCheck` frame numbers come from a synthetic list (`docs/PROFILING.md`), so the cover
grid's true behaviour at 100k covers is unmeasured.

**What.** A `Metric.SCROLL_GRID` sampled with `util/FrameSampler` on the real `ResultGrid` and
the shelves, covers decoded at tile size, and load-more triggered by scroll position instead of
a button when the library is large.

**Files.** `util/PerfCheck.kt`, `data/service/PerfCheckService.kt`,
`ui/screens/home/LibraryBrowseUi.kt`, `ui/components/CoverImage.kt`, `di/ImageModule.kt`.

**Done when.** `PerfCheckTest` covers the new metric and the thresholds, and a 100k fixture run
is written up in `docs/PROFILING.md` with the device it ran on.

## Order of work

1 → 2 → 3 are safe and invisible; 4 protects the handheld; 5 and 6 are the numbers a user feels;
7 needs a big library and a real device, so it is last and it is what the "done when" of 7.6 is
judged on.

## Where this runs

`./gradlew :app:testDebugUnitTest` covers tickets 1–6 (they are pure logic, DAO or view-model
tests). Ticket 7 and the 100k fixture need a device with a large library: `docs/PROFILING.md`
says how to build one with `truncate` and what to record.
