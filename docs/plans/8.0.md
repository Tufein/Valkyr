# 8.0 — one library on several handhelds: task list

The same play list, the same notes, the same profiles on every device you own — with your own
WebDAV folder as the account. Paths are relative to `app/src/main/java/com/tufein/valkyr/`.

What already travels, and what does not:

| Data | Where it lives now | Local backup | Device sync |
| --- | --- | --- | --- |
| Favourites | Room `favourites`, key `consoleId+fileName+profileId` (`data/local/entity/FavouriteEntity.kt` L11) | yes, with `profileId` | only the **active** profile: `DeviceSyncMerge.itemKey` is `console|fileName` (L89) |
| Wishlist, collections | Room | yes | yes (`wishKey` L83, `collectionKey` L99) |
| Notes / journal | `files/game-journal.json` (`data/service/GameJournalService.kt` L39), attachments are `content://` references | yes (`BackupService` section `gameJournal`) | **no** |
| Up next | `files/upnext/upnext[_p_<id>].json` per profile (`data/service/UpNextService.kt` L44, L70) | **no** | **no** |
| Play history | derived: download history + ES-DE `<lastplayed>`/`<playcount>` (`data/service/EsdePlayService.kt` L16–17) + RomM saves | download history only | **no** |
| Ratings and play status | only on RomM (`util/RommGameInfo.kt` `rom_user`, L41/L44); no local column | no | no |
| Profiles and PIN | DataStore `profiles`, `active_profile`, `profile_pin_hash` (`data/local/AppSettings.kt` L84–86, hash in `util/Profiles.kt` L76) | yes, as settings | no |

The machinery to copy is proven: `util/DeviceSyncEngine.kt` (read → three-way merge → conditional
write with a revision mark → apply locally; `library.json` L133, 16 MB cap L135, rollback guard
L116), `util/DeviceSyncMerge.kt` (`tooManyRemovals` L181), `util/DeviceSyncJson.kt` (fixed field
names, `dogmatix-sync` v1), the base file `files/device_sync_base.json`
(`data/service/DeviceSyncService.kt` L340, `resetBase()` L190, triggers L78), and
`util/DavConditionalWriter.kt` for the write itself. `util/SharedWishlistEngine.kt` is the second
example of "one more category, its own format and version" — which is the pattern to follow here
rather than growing `dogmatix-sync` in place.

## 1. Progress becomes local data

**Why.** Play history is derived and ratings live only on a server, so there is nothing to sync.

**What.** A `game_progress` table (console, file, profileId, status, rating, lastPlayedAt,
playCount, updatedAt) written by the places that already know: opening a game, the Up next list,
the RetroAchievements section, ES-DE import in `EsdePlayService`, and RomM sync when a server is
configured (RomM stays the owner when it is on, the local row is the cache and the fallback).
Room version 16 → 17 with `Migration16To17.kt` in the style of `Migration15To16.kt`: pure `plan()`,
unit-tested, registered in `di/DatabaseModule.kt`.

**Files.** new `data/local/entity/GameProgressEntity.kt` + DAO, `data/local/DogmatixDatabase.kt`,
new `data/local/Migration16To17.kt`, `di/DatabaseModule.kt`, `util/PlayHistory.kt`
(clock-skew guard `CLOCK_SKEW_MS = 5 min` L63 becomes a shared rule),
`data/service/PlayHistoryService.kt`, `data/service/EsdePlayService.kt`,
`data/service/RommGameService.kt`, `data/service/GameLaunchService.kt`, new
`Migration16To17Test.kt` and `GameProgressTest.kt`.

**Done when.** A game's status and rating are readable with no RomM server and no network, and the
migration is tested without a device.

## 2. One sync category per thing that travels

**Why.** `dogmatix-sync` v1 refuses a newer file and the keys carry no profile; bolting notes and
Up next onto it would break older builds for everyone.

**What.** Separate `<root>/sync/<category>.json` documents with their own `FORMAT`/`VERSION`, each
an engine + merge + json trio modelled on `SharedWishlistEngine`: `progress.json` (with
`profileId` in the key), `journal.json` (notes text; attachments stay references and say so),
`upnext.json` (per profile), `profiles.json` (name, hidden consoles and tags, PIN **hash**, never
the PIN). Base files per category, next to `device_sync_base.json`.

**Files.** new `util/ProgressSyncEngine.kt`, `JournalSyncEngine.kt`, `UpNextSyncEngine.kt`,
`ProfilesSyncEngine.kt` (+ their `*Json` format files), `data/service/DeviceSyncService.kt`
(triggers and records reuse), `data/service/GameJournalService.kt` (export/apply),
`data/service/UpNextService.kt`, `data/service/ProfileService.kt`, `util/Profiles.kt`,
`util/DavConditionalWriter.kt`, extended `DeviceSyncEngineTest`/`DeviceSyncMergeTest` style tests
on `FakeDavStore` (`app/src/test/java/com/tufein/valkyr/util/CloudFakes.kt`).

**Done when.** Two devices on the same folder end up with the same Up next, notes and progress
after a sync; a device that was offline for a week keeps its own additions and reports the
conflicts it decided; and an older app that reads the folder still opens its own categories.

## 3. Conflicts you decide, once

**Why.** LWW with epoch milliseconds and a 5-minute slack is honest only while both clocks are
close; the roadmap promises "one device going offline for a week does not lose its week".

**What.** Per category: additions always merge, edits that differ are listed for a decision instead
of silently overwritten, and the mass-removal hold (`DeviceSyncMerge.tooManyRemovals`, L181) is
extended to the new categories. One screen for the batch, following the save-conflict pattern,
with a preview of both sides and the choice kept in the record so the same file is not asked twice.

**Files.** new `util/SyncConflict.kt` (pure verdict per category), the four engines above,
`data/service/DeviceSyncService.kt` (`Result.HeldBack` L84 already exists), the hub UI in
`ui/screens/cloud/CloudScreen.kt` (`DeviceSyncCard` L411) plus a conflict sheet,
`data/local/CloudSettings.kt` (records), new strings in `strings_v80_sync.xml` × 7 languages.

**Done when.** A note edited on both devices produces one question, not two overwrites, and
declining leaves both versions reachable.

## 4. Profiles that travel

**Why.** The profile list travels only inside a backup file today, so a second handheld starts
empty and its PIN hash is whatever that device made.

**What.** `profiles.json` from ticket 2, with the active profile staying a local choice: a device
never logs you into another person's profile. The child profile's hidden consoles, tags and PIN
hash move; the PIN itself never does. Settings that are per-device by nature (folders, emulators,
cover-source keys) stay out.

**Files.** `util/Profiles.kt`, `data/service/ProfileService.kt`, `data/local/AppSettings.kt`,
`ProfilesSyncEngine.kt`, `util/SettingSchema.kt` (so nothing syncs what a backup must not carry),
the profiles screens under `ui/screens/`, `ProfilesTest.kt`.

**Done when.** Creating a child profile on one handheld shows it on the other after a sync, with
its PIN still entered locally on each device.

## Order of work

1 is the data model and unblocks everything. 2 is the transport. 3 makes it safe. 4 is small once
2 exists. Tickets 1 and 2 are the two that need care: after this release the app's idea of
"what my library is" is a synced document, so every rule must be written down in the `*Json`
format files the way `DeviceSyncJson` does today.

## Where this runs

All four are unit-testable on `FakeDavStore`, including two-device simulations (two `FakeDavStore`
sides and one base file each — `CloudFakes.kt` already gives `FakeLocal`). The real proof is
physical: two handhelds, one Nextcloud folder, one week of one device being switched off.
